## Context

См. proposal.md — Why. Текущее состояние (изучено в коде):

- Кнопка `#org-gen-pairs` в `portal/inc/org_events.php` (карточка «Слоты», `org_echo_slots_card`) и заглушка в `portal/js/org-events.js`.
- Слоты = `duels` мероприятия: `duel_type` (классика/экспресс/парный), `player1_id`, `player2_id`, `second1_id`, `second2_id`, `situation_id`. Сохранение — `org_slots_save()`.
- Заявки — `meeting_registrations` (`org_event_regs()`): `wants_play/judge/second`, `duel_type_pref`, `comment`, `person_id`.
- Карьера/воронка — `org_people_career()`, `org_funnel_stage()`, `org_reg_heat()` (0/1/2 игры, судил).
- Образец алгоритма-аналога — автоназначение судей `runJudgesAutofill()`: многопроходный жадный, баланс нагрузки, квоты с растущим лимитом `round`, разнообразие через стоимость «соседства».
- Стек: PHP 8.3 + MySQL на портале; деплой FTP.

Ограничение: не трогать таймер, автоназначение судей, протокол.

## Goals / Non-Goals

**Goals:**
- Серверная генерация пар игроков (только `player1_id`/`player2_id`) для слотов классика/экспресс из заявок, с сохранением и вариативностью.
- Реализовать правила 1–5 и модель «пожелания участника / запреты орга».
- Метрика Elo с кэшем.

**Non-Goals (design-level):**
- Секунданты, парный тип, ситуации, судьи, воронка, типы слотов — не в этом дизайне.

## Decisions

### 1. Генерация — серверный обработчик `org_gen_pairs`
Новый action в `org_events.php`, по образцу `org_slots_save`. Возвращает redirect на `#slots`. Альтернатива (клиентский JS) отклонена: правила требуют БД (карьера, Elo, история пар), а сохранение уже серверное.

### 2. Алгоритм — многопроходный жадный (как судьи)
Вход: слоты типов классика/экспресс (в порядке `sort_order`) + пул заявок.
- **Пул:** `wants_play = true`, нет пометки орга «не играть», тип слота не в запрещённых типах орга.
- **Квота:** лимит 1 поединок на человека; внешний цикл `round` поднимает лимит до 2, пока есть незаполненные слоты и свободные люди.
- **Порядок выбора:** по приоритету. Группа A (games < 3) — по ступени воронки (без игр → 1 → 2), внутри ступени несудившие — последними; затем Группа B — по давности последней игры (давние раньше).
- **Сборка слота:** берём наивысшего приоритета свободного человека как `p1`; `p2` выбираем по минимальной стоимости:
  - **вето:** если оба новички (`games = 0`) — недопустимо;
  - `cost += w_pair * (свежесть последней пары)` — штраф за недавнюю пару (окно ~90–180 дней);
  - `cost += w_elo * |Elo_a − Elo_b|` (с фолбэком на карьеру при < 3 играх);
  - пожелание типа: мягкий штраф, если тип слота не в предпочтении;
  - `wants_judge`: слабый сдвиг приоритета (в пользу тех, кто ещё не играл / ср. п.1.2).
- **Вариативность:** при равной стоимости выбор случайный (`shuffle`), поэтому повторный запуск даёт другой вариант. Дополнительно можно явно исключать пары из предыдущей раскладки.

### 3. Elo — кэш в БД
- Таблица `person_elo(person_id PK, elo DOUBLE, games INT, updated_at DATETIME)`.
- Расчёт в PHP: хронологически по `duels`, исход — большинство голосов `duel_judges.vote`. Классика/экспресс — 1×1; **парный — 2×2, но Elo считаем каждому участнику стороны** (игрок и его второй игрок) как в классике: опорный рейтинг стороны — **максимальный Elo** её участников (сильнейший), дельта применяется персонально каждому. Опорный рейтинг стороны — это лишь замена «одного соперника» для формулы ожидаемого исхода (в парном соперников двое); к назначению пар это отношения не имеет.
- Параметры: старт 1500, K = 32 (тюнингуемые константы).
- Пересчёт: при импорте протокола (хук там же, где импорт поединков) + разовый бэкфилл-скрипт.

### 4. Модель заявки — пожелания vs запреты
- Пожелания участника — существующие поля: `wants_play/judge/second`, `duel_type_pref` (как сейчас, одиночный), `comment`. Не меняем семантику.
- Пометки орга — **новые поля** `meeting_registrations`: `org_no_play TINYINT`, `org_banned_types` (SET/строка: `классика,экспресс,парный`). Видны/редактируются только на странице орги; участнику не показываются.
- Запрет орга = жёсткий фильтр; пожелание = мягкий вес. Реализация veto-типов: человек исключается из пула слота нужного типа.

### 5. Авто-добавление секунданта в заявку
В обработчике выбора секунданта в слоте: если выбранный `person_id` не имеет заявки в мероприятии — создать `meeting_registrations` (`wants_second = 1`, `full_name` из `people`). Отдельное действие, не связано с генерацией пар.

## Risks / Trade-offs

- **Устаревший/пустой Elo** → фолбэк на карьеру при < 3 играх; бэкфилл обязателен до первого запуска.
- **Мало заявок / людей в типе** → слоты остаются частично пустыми; сортировка идёт по «сначала заполняем наиболее приоритетных», не выдумываем людей.
- **«Другой вариант» неотличим** → рандомизация равнозначных кандидатов + исключение пар последней раскладки.
- **Живые данные (нарушение посимпатичнее)**: генерация перезаписывает `p1/p2` существующих слотов — орг может откатить повторной генерацией или правкой. Слоты с судьями: не трогаем? Решение: генератор **не перезаписывает слот, у которого уже есть судьи** (аналогично запрету удаления слота с судьями).
- **Парный в Elo** — считается каждому участнику стороны (опорный рейтинг стороны — максимальный Elo, дельта персонально). Риск: секундант как второй игрок может быть сильнее/слабее как игрок; но такова выбранная модель.

## Migration Plan

1. Миграция БД: `CREATE TABLE person_elo`; `ALTER meeting_registrations ADD org_no_play, org_banned_types`.
2. Бэкфилл Elo (разовый скрипт из `scripts/`).
3. Реализация обработчика `org_gen_pairs`, UI-кнопки, полей пометок орга, авто-добавления секунданта.
4. Проверка на dev/тестовом мероприятии; выкладка — только по явной команде (deploy FTP).
5. Rollback: кнопка возвращается в заглушку; новые таблицы/поля не мешают (nullable/дефолт).

## Open Questions

- Пороговые веса `w_pair`, `w_elo`, окно истории пар (90 vs 180 дней) — тюнингуются после первых запусков, спецификацию не меняют.
