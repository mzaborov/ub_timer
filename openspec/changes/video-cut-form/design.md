## Context

Портал уже хранит видеозаписи в таблице `videos` (`event_id`, `duel_id`, `situation_id`, `url`, `video_type`), а просмотр идёт через `media.php` (Range-прокси к Google Drive) и `player.php`. Поединки и события протокола доступны в БД; `protocol_events` содержит `moment_sec` и серверное время, `duels` — порядок и игроков. Сейчас разметка и нарезка выполняются вручную вне системы.

Стек портала — чистый PHP/JS на общем хостинге; устанавливать ffmpeg на хостинг нельзя. Записи Zoom весят гигабайты, поэтому обрабатывать их нужно на машине организатора.

## Goals / Non-Goals

**Goals**
- Веб-морда формы живёт в портале и работает в обычном браузере.
- Тяжёлая обработка (ffprobe/ffmpeg, чтение файла, нарезка) — локально на ПК организатора.
- Минимум ручной работы: границы поединков предлагаются по протоколу и сцене, человек только проверяет и двигает.
- Публикация результата сразу в Drive и `videos`.

**Non-Goals**
- Обработка на хостинге, хранение исходников на портале.
- Покадровая ручная разметка и монтаж (только границы поединков).
- Автоматическая загрузка в YouTube/Telegram.

## Decisions

### 1. Портал = UI, локальный Python-сервис = обработчик
Портал отдаёт страницу формы, данные мероприятия и принимает итоговые записи в `videos`. Локальный сервис `tools/video-cutter/` на FastAPI слушает `127.0.0.1`, читает файл, вызывает `ffprobe`/`ffmpeg`, режет и загружает в Drive.

Почему не ffmpeg.wasm в браузере: запись 2–3 часа не помещается в память, скорость и стабильность неприемлемы. Почему не сервер: хостинг без ffmpeg и места, загрузка гигабайтов на него бессмысленна.

### 2. Обмен между порталом и сервисом
`POST /api/jobs` — создать задачу: путь к файлу или Drive-ссылка, мероприятие, список поединков с временами, параметры кодирования. `GET /api/jobs/{id}` — статус и прогресс. `POST /api/jobs/{id}/cut` — нарезка. `POST /api/jobs/{id}/publish` — загрузка. Токен выдаётся порталом на сессию и проверяется сервисом; CORS ограничен доменом портала.

### 3. Синхронизация записи и протокола
Абсолютное время старта записи задаётся вручную (дата/время первого кадра) или берётся из имени файла Zoom. Границы поединков берутся не из первого/последнего события, а по смыслу: начало #1 — `началоПоединка`; начало #N — `решениеСудей` предыдущего поединка (закрытие формы судей); конец — `завершение` этого поединка. Автоматическое `раскрытиеСитуации` после предыдущего поединка — ложный маркер начала, его не используем. Если протокола нет, границы строятся по детекции сцены (`ffmpeg -vf "select='gt(scene,0.4)',showinfo"`) и ключевым кадрам. Глобальный сдвиг и индивидуальные правки хранятся в черновике задачи.

### 4. Нарезка
`ffmpeg -ss <start> -to <end> -i <src> -c:v libx264 -preset <p> -crf <n> -c:a aac -b:a 160k -movflags +faststart <out>`. Перекодирование видео обязательно (точность реза по кадрам), звук можно копировать при совместимом кодеке. Имена — по шаблону из спеки, кириллица сохраняется, запрещённые символы заменяются. Старт фрагмента выравнивается по ближайшему полному кадру слева: форма считает `startSec` по сетке `fps` (поле «fps записи», для Zoom обычно 25), сервис перед резом пересчитывает по `ffprobe` PTS кадров и ставит `-ss` на PTS кадра, чтобы не начинать с середины кадра.

### 5. Публикация
Загрузка в Drive — через `rclone` (уже знакомый инструмент) или Drive API; в design фиксируем `rclone` как основной путь, API — как альтернативу. После загрузки портал получает ссылки и делает `INSERT INTO videos`; при наличии записи для `duel_id` — `UPDATE url/title`.

### 6. Хранение черновика
Черновик разметки — JSON в локальном каталоге сервиса (`state/<job>.json`), чтобы можно было закрыть браузер и продолжить. В БД черновики не пишем, чтобы не плодить сущности.

### 7. Стартовая папка для выбора записи
Браузер не позволяет задать произвольную стартовую папку для `<input type=file>`: доступны только well-known каталоги или ранее выданный `FileSystemHandle`, а в Яндекс.Браузере File System Access API недоступен. Поэтому нативный выбор файла в локальном сервисе использует `VIDEO_CUT_DEFAULT_DIR`; по умолчанию `%USERPROFILE%\Documents\Zoom` (Windows) или `~/Documents/Zoom`. Веб-форма показывает подсказку с типовым путём и остаётся fallback-предпросмотром.

## Risks / Trade-offs

- [Долгая нарезка и нехватка места] → проверять свободное место до старта, писать во временный каталог, удалять фрагменты после успешной загрузки.
- [Неточная синхронизация] → обязательное превью стартового/финального кадра и глобальный сдвиг; при расхождении > 2 с показывать предупреждение.
- [Разные кодеки/переменный fps] → `ffprobe` до старта, принудительный CFR и перекодирование.
- [Дубли записей `videos`] → проверка по `duel_id` перед вставкой, режим «заменить/пропустить».
- [Безопасность локального сервиса] → только loopback, токен, проверка Origin, без приёма произвольных путей вне выбранного файла.
- [Кириллица в именах и Drive] → явная UTF-8 обработка и проверка после загрузки.

## Migration Plan

1. Выложить портал с новым разделом (раздел скрыт, пока сервис не запущен).
2. Установить `tools/video-cutter` на машину организатора (Python 3.11+, ffmpeg, rclone), настроить kvault для Drive.
3. Прогнать форму на коротком тестовом фрагменте, затем на реальной записи.
4. Откат: убрать пункт меню и маршрут; уже созданные записи `videos` остаются рабочими.
