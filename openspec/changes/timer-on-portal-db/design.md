## Goals / Non-Goals

**Goals:**
- Чтение канона встречи из общей MySQL (same-host эндпоинт) и загрузка состава в часы (пункт меню «из БД»).
- Запись хода боя в общую MySQL: append-only **СобытиеПротокола**, актуальные **Поединок**/**Судья**/**голос**, **ЖурналИзмененияПоединка**.
- Внедрение как **второй независимый режим**: чтение и запись из общей БД; выбор режима — при загрузке расписания; Google-режим сохраняется; работа часов без БД сохраняется.
- Зафиксировать политику пустого исторического протокола.

**Non-Goals (design-level):**
- Перенос алгоритма судей в PHP; новые доменные сущности и таблицы; победитель/счёт как атрибут; CRM/бот/Zoom/видео/рейтинг; восстановление прошлого лога.

## Decisions

### 1. Эндпоинт на хосте часов, прямой доступ к общей БД
Новый PHP-эндпоинт кладётся **рядом с часами** (`timer.zaborov.ru`, same-origin) и пишет/читает общую БД `u10190_ubtimer` напрямую через `dirname(__FILE__).'/../db.inc.php'` — как уже делает [points.php](../../../points.php#L50). Часы и портал — соседние папки одного аккаунта Masterhost; БД и `db.inc.php` общие.
- Следствия: **CORS не нужен** (same-origin), **новый секрет-ключ не нужен** (доступ как у прочих PHP-страниц часов; аутентификация — существующая, cookie `ub_me`/орг-пароль, если понадобится).
- **Чтение:** эндпоинт отдаёт список мероприятий и состав выбранного мероприятия (поединки + судьи + ситуации + ФИО людей), в форме, близкой к `duelsList`, но с `*Id`, а не только ФИО.
- **Запись:** эндпоинт принимает события протокола и актуальный слот.
- Отклонённая альтернатива: API на портале (PHP 8.3) — даёт `mysqli`/prepared statements, но добавляет второй origin, CORS и ключ между сайтами одного аккаунта. План 06 (§3) предлагал её из общего правила «современный API на 8.3»; для узкого эндпоинта на своём же хосте это переусложнение. Если понадобится сложная логика (Elo, агрегаты), её можно вызывать с портала отдельно.
- Ограничение: код на PHP 5.2.17 (EOL, `mysql_*` без prepared statements). В проекте это уже принято (`points.php`).

### 1a. Инвариант: работа без БД
Интеграция **аддитивная**. Часы MUST работать при недоступной/отсутствующей БД: загрузка из файла и локальная сессия (`ub-timer-online-state`) сохраняются. При недоступной БД чтение/запись молча деградируют (сообщение в UI, события — в локальную очередь), бой не прерывается. Поэтому LS **не удаляется**, а остаётся офлайн-снимком.

### 2. Клиентский модуль чтения/записи портала
Новый модуль(и) в `js/`, подключаемые в `index.html` в существующем порядке (после `schedule.js`/`live-protocol.js`, до/рядом с `init.js`). Пункт «из БД» добавляется в `<ul id="load-schedule-submenu-menu">` и в роутер `onLoadScheduleSubmenuItem_`. Загрузка из БД заполняет `duelsList` и `duelAssignments` (с `*Id` из базы), `people` — из справочника людей в базе.

### 3. Маппинг Live-четвёрки и остальных событий в канон
| Сейчас Google | В БД |
|---------------|------|
| состав (игроки/судьи) | **Поединок** + **Судья** + **ЖурналИзмененияПоединка** |
| ситуация `00` | привязка **Ситуация** + событие `расчетСитуации` |
| «Начинал» = Команда N | событие `жеребьёвка` + перестановка `*Id` (в домене поля «кто начинал» нет) |
| голос | событие `голос` (новое на **каждое** изменение) + материализация текущего значения в `duel_judges.vote` |
Плюс то, что Google не хранил логом: пауза, протест, смена хода, роли, старт/конец раунда, раскрытие названия, завершение.

### 4. Два источника: журнал ↔ материализация
- **`protocol_events`** — append-only истина хода; все существенные действия, **включая каждое изменение голоса** (смена голоса = новое событие, старое не перезаписывается).
- **`duel_judges`** — материализованный снимок: список судей, коллегия, **текущий** голос (upsert, «последний клик побеждает») и флаг **`agreed`** («согласился судить»). Его читает рейтинг (`rating.php`/`elo.php`), поэтому рейтинг не трогаем.
- **Отдельной `duel_results` нет.** Роль «второго места» играет `duel_judges`. На завершении сверяем: итог по журналу (события `голос`) ↔ текущие `duel_judges.vote`. Расхождение = сигнал разбираться (два источника независимы и переживают частичный отказ записи).

### 4a. Согласие судьи («зелёная ячейка»)
Зелёное подтверждение ячейки судьи означает **«судья согласился судить»** — это факт, а не UI-метка.
- **Материализация:** `duel_judges.agreed` (TINYINT, «текущее согласие») — так согласие видно на любом устройстве.
- **Журнал:** событие `согласиеСудьи` в `protocol_events` (кто, поединок, момент; включил/снял) — история.
- Тумблер on/off = «согласился» / «снял согласие».
- Игроки/секунданты: подсветка остаётся UI-меткой в LS (в домен и БД не идёт).

### 5. Алгоритм судей остаётся в JS
Эндпоинт принимает **результат** (список **Судья** с коллегией и голосом), а не пересчитывает. Иначе два расхождения с JS-автоназначением.

### 6. Канал записи следует за источником (без dual-write)
Часы запоминают источник загрузки состава и направляют события туда же: Google-состав → Live в Google GAS (как сейчас); состав из БД → запись в БД. **Одновременная запись в оба канала не делается** — иначе одно событие дублируется, а Google-сетка и БД расходятся.
- Google-режим остаётся полноценным; cut Google не планируется.
- Смена источника применяется к последующим событиям; ранее записанное не переносится и не дублируется.
- Знание источника хранится в контексте загрузки расписания (аналог `googleCompositionContext`) — отдельного «режима» в домене нет.

### 7. Индемпотентность записи и офлайн
Идентичность протокола — по моменту события, не `UNIQUE(seq)`. Клиент держит очередь при обрыве сети/недоступной БД и отправляет её при восстановлении (один поток, без дублей и потери порядка). Полный офлайн-sync не изобретаем: снимок UI живёт локально.

### 8. Люди (Человек) — из базы, ярлыки вычисляются
ФИО подставляются по `*Id` из справочника людей; параллельный локальный каталог `p_N` в БД не создаём (согласуется с планом §3).
**Решение (2026-10-14):** ярлыки назначения (новичок / опытный / орг / судья ФУБ), которыми кормится автоназначение, **вычисляются из БД**, ручные радио убираются. Основой служат воронка, роли мероприятия и круги:

| Ярлык | Источник | Правило |
|---|---|---|
| **новичок** | воронка `org_funnel_stage` | ступени `без игр` / `посудил` / `сыграл 1` / `сыграл 2` — вся Группа A (<3 игр) |
| **опытный** | воронка | ступени `профи` / `наставник` (3+ игр) |
| **орг** | роли мероприятия `event_organizers` (enum `РольОрганизатора`) | группа I «в процессе игры»: `экспертныйКомментарий`, `показывалЧасы`, `настраивалКомнатыZoom`; группа II: `велЗапись`, `планированиеМероприятия`, `подведениеИтогов` |
| **судья ФУБ** | круги `ЧленствоВКруге.степеньВовлечения` | «Профессиональный судья» |

- Арбитр мероприятия (`events.referee_person_id`) ярлыка не даёт — он не участвует в поединках.
- Приоритет, если человек подходит под несколько ярлыков: **судья ФУБ > орг > воронка** (согласуется с порядком автоназначения: ФУБ ставятся первыми, орги — в последнюю очередь).
- `Человек.активен = false` → исключён из автоназначения.
- В режиме **без БД** — фолбэк: остаются локальные пометки в LS (как сейчас). Сам алгоритм автоназначения не меняется — меняется только источник ярлыков.

### 9. Восстановление — только из localStorage (heartbeat отложен)
**Решение (2026-10-14):** после закрытия/перезагрузки вкладки часы восстанавливают **фазу и остатки таймеров из localStorage** (`ub-timer-online-state`), как сейчас. Канон при доступной БД восстанавливается из БД (состав, судьи, голоса, лог), при недоступной — из локального снимка. `phase`, остатки бубликов, текущий раунд/ход, подсветка судьи остаются в LS.
- Восстановление **остатков таймеров из БД (heartbeat)** в этом изменении **не делается** — отдельный вопрос на потом (§4.4 плана). Следствие: «продолжить минуты на втором экране» без LS невозможно, второй экран поднимает канон из БД и стартует с паузы.

### 10. Набор событий протокола (расширение)
**Решение (2026-10-14):** набор `ТипСобытияПротокола` расширяется (см. `05_доменная_модель.yaml`):
- добавляются **«начало поединка»**, **«корректировка часов»**, **«решение судей зафиксировано»**;
- **пауза** пишется дважды (вход и выход);
- при выборе (открытии) поединка фиксируется **«раскрытие ситуации»** — в т.ч. для обычной ситуации из БД (не только `скрытыйДоНачала`);
- «начало поединка» и «старт раунда» — **разные** события, пишутся оба: «начало поединка» при нажатии кнопки, «старт раунда» при запуске отсчёта (и на каждый новый раунд).

### 11. Порядок поединков (перестановка)
**Решение (2026-10-14):** порядок поединков **хранится там же, откуда читается состав** — в `duels.sort_order` (ключ `idx_duels_event (event_id, sort_order)`). Перестановка доступна:
- при **планировании** на портале (рабочее место орга) — кнопки вверх/вниз;
- **во время онлайна** в часах — участник просится в начало/конец; список часов перестраивается, новый порядок пишется в БД; текущий поединок не теряется.
Нового поля и новых сущностей нет.

### 12. Просмотр лога оргом (портал)
**Решение (2026-10-14):** на **карточке мероприятия** в рабочем месте орга — read-only просмотр журнала поединков: `protocol_events` (события хода) и `duel_change_log` (правки состава/судей), с фильтром по поединку. Доступ — только у авторизованного орга. **Публичная «красивая» визуализация** (в стиле статистики баскетбольного матча) для остальных — **не сейчас**, записана в идеи ([docs/планы/идеи.md](../../../docs/планы/идеи.md)).

### 13. Контракт read-эндпоинта (шаг 2)
**Решение (2026-10-14):** файл — `db.php` на хосте часов (рядом с `points.php`), один файл на чтение и (позже) запись через `?action=`. PHP 5.2, общий `../db.inc.php`, same-origin, без CORS и ключа. Ответ — `application/json`; ошибка — `{"ok":false,"error":"..."}`.

Действия:
- `?action=events&scope=today|upcoming` → `{"ok":true,"events":[{id,title,event_type,starts_on,starts_at,status}]}`. `scope=today` — `starts_on=CURDATE()` (боевой); `scope=upcoming` — `status<>'Проведено'` (тест/локально). Порядок — дата вниз. Режим определяет клиент по hostname (как favicon: `timer.zaborov.ru` = прод).
- `?action=event&id=<int>` → `{"ok":true,"event":{...},"duels":[...],"people":[...]}`:
  - `duels[]`: `{id, sort_order, duel_type, prep_mode, round_minutes, referee_qty, notes, situation:{id,code,num,duel_type,description,roles_json}|null, player1/second1/player2/second2:{id,full_name}|null, judges:[{person_id,college,vote}]}` — `ORDER BY sort_order`.
  - `people[]`: только задействованные (участники + судьи): `{id, full_name, is_active, experience_label, stats:{played,judged,seconded}}`.

Ярлык `experience_label` считается **на сервере** (SQL по воронке/кругам/орг-ролям): `судья ФУБ`(круг «Профессиональный судья») → `expert`, `орг`(роли мероприятия группы I/II) → `org`, воронка 3+ игр → `experienced`, иначе `novice`; приоритет ФУБ > орг > воронка. `situations` не имеет колонки имени — `SituationNum`/`SituationName` = `code`; при `situation_id IS NULL` — случайный слот (`Случайная ситуация`). Клиент собирает `duelsList` в форме `buildDuelsListFromGoogleMeeting_`, `duelAssignments` — с персональными `*Id` из БД.

## Risks / Trade-offs

- **Два писателя состава** — орги уже INSERT/UPDATE `duels`; во время онлайна актуальной сеткой владеют часы. Не затирать лог; при конфликте приоритет — последняя запись из часов.
- **PHP 5.2 на хосте часов** — эндпоинт на legacy-PHP: без prepared statements, аккуратно с экранированием; сложную логику сюда не тащим.
- **Открытый same-origin эндпоинт** — без ключа любой может POST на запись (как и к `points.php`). Приемлемо для внутреннего инструмента; при необходимости — прятать за существующей cookie/рест-проверкой, но нового секрета не вводим.
- **Экспресс 5 слотов формы vs COUNT(Судья)** — пустые слоты формы не писать как **Судья** (инвариант `unknown-judge-placeholder`).
- **Индемпотентность и порядок** — при сетевых сбоях риск дублей; решается моментом события и очередью клиента.
- **Ошибочный источник** — если контекст источника потерян (перезагрузка страницы), часы могут уйти не в тот канал; источник хранится вместе с загруженным расписанием и восстанавливается из снимка сессии.
- **Работа без БД** — обязательный режим: без базы бой идёт локально, события копятся локально; БД — усилитель, а не обязательное условие.
