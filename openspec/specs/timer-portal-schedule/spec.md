# timer-portal-schedule Specification

## Purpose
Позволяет часам загружать состав встречи (мероприятие, поединки, судей, ситуации, людей) напрямую из общей MySQL-базы, к которой у часов есть прямой доступ на том же хостинге, не полагаясь на published CSV Google-таблицы и не ломая работу часов без БД.

## Requirements

### Requirement: Загрузка встречи из общей базы

Часы SHALL предоставлять пункт меню загрузки расписания из базы рядом с существующими пунктами «из Google» и «из файла», не заменяя их. По выбору пункта часы MUST получить список мероприятий и позволить выбрать одно, после чего загрузить его состав.

#### Scenario: Пункт меню доступен
- **WHEN** оператор открывает меню загрузки расписания
- **THEN** среди пунктов есть «из базы» рядом с пунктами «из Google последний», «из файла», «из Google выбрать»

#### Scenario: Загрузка выбранного мероприятия
- **WHEN** оператор выбирает мероприятие из списка
- **THEN** состав мероприятия загружается в часы, отображается список поединков, выбирается первый незавершённый поединок

#### Scenario: Пустой список мероприятий
- **WHEN** в базе нет мероприятий с датой начала
- **THEN** часы сообщают, что мероприятий нет, и не изменяют текущий состав

### Requirement: Список мероприятий из базы

Часы SHALL получать список мероприятий (идентификатор, название, тип, дата и время начала, статус) из общей базы. Мероприятия MUST быть упорядочены по дате начала, новые доступны сверху.

#### Scenario: Список отсортирован
- **WHEN** открыт выбор мероприятия
- **THEN** мероприятия показаны в порядке даты начала, и по каждому видно название, тип и статус

### Requirement: Состав поединков из канона

Часы SHALL собирать список поединков из канонических данных: порядок, тип поединка, длительность раунда в минутах, режим подготовки, привязка к ситуации и стороны поединка (игрок и секундант/второй игрок — по каждому `*Id`). Имена игроков и секундантов MUST подставляться из справочника людей, а не из текстовых полей сетки.

#### Scenario: Классика
- **WHEN** мероприятие содержит поединок типа «классика» с игроками и секундантами
- **THEN** в часах у поединка заполнены игрок 1/2 и секундант 1/2 их ФИО, тип «Классика» и длительность раунда из базы

#### Scenario: Экспресс без секундантов
- **WHEN** поединок типа «экспресс»
- **THEN** стороны содержат только игроков, секунданты пусты, форма рассчитана на 5 судей

#### Scenario: Порядок поединков
- **WHEN** мероприятие содержит несколько поединков
- **THEN** поединки в списке часов идут в порядке, заданном в базе

### Requirement: Судьи и коллегии из канона

Часы SHALL загружать актуальный список судей поединка с их коллегиями и текущими голосами. Судья без указанного человека MUST отображаться как пустой слот с подписью «Судья N», а не как запись с ФИО.

#### Scenario: Судья без человека
- **WHEN** в базе у поединка есть запись судьи без человека (голос без ФИО)
- **THEN** в часах это пустой слот формы с подписью «Судья N», инвариант вместимости не нарушен

#### Scenario: Голос уже проставлен
- **WHEN** у судьи в базе сохранён голос
- **THEN** при загрузке поединка этот голос восстановлен в форме голосования

### Requirement: Ситуации и резолв из банка базы

Часы SHALL брать тексты ситуаций (код, номер, название, описание, роли) и банк ситуаций из общей базы. Слоты случайной ситуации (`00` / `00Э`) MUST резолвиться из банка базы, а не из CSV Google.

#### Scenario: Текст ситуации из базы
- **WHEN** поединок привязан к ситуации в базе
- **THEN** в часах показывается название, описание и роли из базы

#### Scenario: Резолв случайной ситуации
- **WHEN** оператор бросает кубик на слоте `00` / `00Э` при составе из базы
- **THEN** ситуация выбирается из банка базы того же типа

### Requirement: Единственный источник при загрузке из базы

При загрузке состава из базы часы MUST NOT обращаться к published CSV Google за составом или банком ситуаций. Тип расписания (классика/парный/экспресс) и длительности раундов MUST соответствовать данным базы.

#### Scenario: Нет обращения к Google
- **WHEN** состав загружен из базы
- **THEN** часовой клиент не запрашивает Google-состав и не подтягивает CSV банка

### Requirement: Справочник людей с вычисляемыми ярлыками

При работе с базой часы SHALL получать по каждому человеку данные для вычисления ярлыков назначения (новичок / опытный / орг / судья ФУБ) и **вычислять** их, а не использовать ручные пометки. Ярлыки вычисляются из трёх источников:

- **новичок / опытный** — по ступени воронки: `без игр` / `посудил` / `сыграл 1` / `сыграл 2` (вся Группа A, <3 игр) → **новичок**; `профи` / `наставник` → **опытный**;
- **орг** — по наличию обслуживающей роли мероприятия (`event_organizers`): Экспертный комментарий, Демонстрация часов, Zoom, Запись, Планирование мероприятия, Подготовка итогов и закрытие;
- **судья ФУБ** — по членству в круге со степенью «Профессиональный судья».

Если человек подходит под несколько ярлыков, приоритет: **судья ФУБ > орг > воронка**. Арбитр мероприятия (`events.referee_person_id`) ярлыка MUST NOT получать. Неактивные люди MUST исключаться из автоназначения. В режиме без БД часы SHALL сохранять возможность работы с локальными пометками (фолбэк).

#### Scenario: Ярлык новичка по воронке
- **WHEN** человек сыграл 0, 1 или 2 поединка (вся Группа A)
- **THEN** часы вычисляют ярлык «новичок»

#### Scenario: Ярлык опытного по воронке
- **WHEN** человек сыграл 3 и более поединков (профи / наставник)
- **THEN** часы вычисляют ярлык «опытный»

#### Scenario: Ярлык орга по роли мероприятия
- **WHEN** у человека есть обслуживающая роль мероприятия (например, «Показывал часы» или «Вел запись»)
- **THEN** часы вычисляют ярлык «орг»

#### Scenario: Арбитр не получает ярлыка
- **WHEN** человек — главный арбитр мероприятия
- **THEN** из этого он не получает ярлык назначения

#### Scenario: Приоритет ярлыков
- **WHEN** человек и член круга «Профессиональный судья», и имеет обслуживающую роль мероприятия
- **THEN** ярлык — «судья ФУБ»

#### Scenario: Неактивный человек
- **WHEN** человек помечен неактивным в базе
- **THEN** он исключён из автоназначения судей

#### Scenario: Работа без базы
- **WHEN** база недоступна
- **THEN** автоназначение опирается на локальные пометки, как раньше

### Requirement: Работа без БД

Часы MUST сохранять полную работоспособность при недоступной или отсутствующей базе. Загрузка расписания из файла и локальная сессия MUST работать независимо от БД; при недоступности базы часы MUST показать понятное сообщение и MUST NOT изменять текущий загруженный состав.

#### Scenario: База недоступна
- **WHEN** запрос к базе завершается ошибкой или БД не сконфигурирована
- **THEN** часы показывают сообщение и сохраняют прежний состав без изменений

#### Scenario: Загрузка из файла без БД
- **WHEN** оператор загружает расписание из файла, а БД недоступна
- **THEN** расписание загружается как обычно, без обращений к базе
