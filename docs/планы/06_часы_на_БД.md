## 1. Цель

Таймер (`timer.zaborov.ru`, `index.html` + `js/`) **читает и пишет MySQL** `u10190_ubtimer` через **тонкий PHP-эндпоинт на хосте часов** (PHP **5.2.17**, `mysqli`, `../db.inc.php`) — **same-origin, без CORS и нового ключа**: часы и портал — соседние папки одного аккаунта Masterhost и делят одну БД. Образец прямого доступа — [`points.php`](../../points.php). Сложную логику на PHP 5.2 не тащим.

Google у часов: остаётся **полноценным режимом**. Запись идёт по **источнику загрузки** (Google-состав → Live в GAS; состав из БД → БД), одновременной записи нет. **Cut Google не делаем.**

Часть **localStorage** переезжает в БД (не весь снимок сессии). Канон (состав/голоса/лог) в БД-режиме берётся из БД; снимок UI/часов (фаза, остатки таймеров) **остаётся в LS** — в домене это не источник истины. Нужен ли кэш/heartbeat этого снимка ещё и в БД (второй экран, очистка LS) — **к обсуждению**, §4.4 (в этом изменении heartbeat не берём).

Критерий смысла: онлайн можно провести с другого устройства/браузера, не потеряв состав, ситуацию, судей, голоса и лог боя.

### Куда уходит протокол

Четыре канала, они **не одно и то же**:

1. **Live → Google** (`js/live-protocol.js` → GAS Web App): 4 события в сетку состава — состав судей/игроков, случайная ситуация, «Начинал», голос. Ключ `LIVE_PROTOCOL_KEY` (default / localStorage). Победителя и счёт в ячейки **не** пишет (формулы таблицы).
2. **localStorage** ключ `ub-timer-online-state` — полный снимок сессии (см. §4). Пишет `saveProtocolStateToLocalStorage` (`schedule.js`); вызывают `core.js` (тик/ход/пауза), `referees.js` (голос), `toolbar-sound.js` (финиш), `protocol.js` (восстановление).
3. **Excel** «Сохранить в файл» / «Сохранить статус онлайна» — выгрузка из памяти/LS, не источник истины.
4. **MySQL** — часы **не** пишут. Орги на портале уже трогают `duels` (добавить/удалить/порядок), но **не** live-протокол.

`js/core.js`: прямой Google нет; на старте боя — `notifyLiveProtocolStarted_`; на тике/смене — `saveProtocolStateToLocalStorage`.

## 3. Канон to-be: какие сущности трогают часы

Только классы yaml. Новых таблиц (`timer_sessions`, `ПротоколПоединка`, слоты team1/2) **нет**.

| Класс | Часы | Заметка |
|-------|------|---------|
| **Мероприятие** | чтение (выбор встречи) | список / карточка для загрузки состава |
| **Поединок** | чтение + запись актуального состава `*Id`, ситуации (ассоциация), `режимПодготовки`, `длительностьРаундаМин`, вместимость формы 5/7/9 (`referee_qty` в черновике маппинга) | после жребия — перестановка `игрок1`/`игрок2`, не поле «кто начинал» |
| **Судья** | чтение + запись актуального списка, `голос` и `согласовано` | результат алгоритма JS, не PHP; пустой слот формы — не запись; голос без ФИО — `idУчастника` null, коллегия `неизвестна`; `согласовано` — «судья согласился судить» (зелёная ячейка), история событием `согласиеСудьи` |
| **СобытиеПротокола** | запись (append-only лог) | источник истины хода боя: старт/конец раунда, смена хода, пауза, протест, голос (на каждое изменение), выборРоли, жеребьёвка, расчетСитуации, раскрытиеСитуации, согласиеСудьи, завершение |
| **ЖурналИзмененияПоединка** | запись, если часы меняют состав/судей/ситуацию | история; не парные план/факт |
| **Ситуация** | чтение (join / кубик 00) | подпись = код+номер; банк на странице уже из API |
| **Человек** | чтение (ФИО слотов, справочник для назначения) | не создавать параллельный каталог `p_N` в БД |

Не трогаем этим планом: Круг / членство (кроме косвенно, если ярлыки назначения **вычислять** с портала), Видео, Регистрация, УчастиеВОрганизации, Наблюдатель, баллы/рейтинг как сущности. Победитель/счёт — вычисление по `Судья.голос`, не атрибут `Поединок`. Снимок `duel_results` — витрина, не домен; **решение (2026-10-14): не нужна** — вся информация для рейтинга уже есть на портале (`duels` + `duel_judges` → `rating.php`/`rating_calc.php`, сила — `person_elo`).

Инварианты, которые часы обязаны соблюдать при записи: `express-judges-5`, `express-no-seconds`, `qty-matches-slots`, `cannot-judge-own-duel`, `unknown-judge-placeholder`, `protocol-is-event-log`, `votes-on-judge`, `hidden-ne-random`, `round-minutes-5-4-1`. Алгоритм судей **остаётся в JS** (см. риски).

### 4.3. Снимок LS и канон в БД (вместо dual-run)

2. **Канал записи следует за источником загрузки**: Google-состав → Live в Google (как сейчас); состав из БД → запись в БД. **Одновременной записи в оба канала нет** (никакого dual-write).
3. LS (`ub-timer-online-state`) остаётся **локальным снимком/резервом** во всех режимах: фаза, остатки таймеров, раунд/ход. Канон (состав, судьи, голоса, лог) в БД-режиме берётся из БД.

### 4.4. Восстановление вкладки (**к обсуждению**, не канон)

Факт as-is: закрытие вкладки / F5 не теряет бой, если тот же браузер. Ключ `ub-timer-online-state`. Пишет `saveProtocolStateToLocalStorage` (тик раунда, ход, пауза, голос, финиш, выбор поединка). При загрузке `checkRestoreProtocolBanner` показывает баннер, если в LS есть `duelsList` и хотя бы одно из: фаза `round`/`judges`, «реальные» данные протокола (`Winner` / `RoundDurations` / `JudgeVotes`), словарь `people`. По «Восстановить» — `restoreProtocolStateFromLocalStorage` → `duelChoosed` → `applyRestoredSessionState`. Часы после restore **на паузе** (`clock_is_active = false`); остатки минут — как в последнем тике, не вычитаются по wall-clock.

Чтобы **продолжить тот же бой** на этом устройстве, restore реально поднимает:

| Нужно продолжить бой | Откуда в LS | Уже в плане 06 |
|----------------------|-------------|----------------|
| список поединков, имена, тип, минуты, Hidden | `duelsList` | канон → **Поединок** |
| состав слотов и судьи | `duelAssignments` (+ `people` как локальный справочник) | канон → **Поединок** `*Id` / **Судья** / **Человек**; `people` — вопрос §4.2 |
| ситуация, раскрытие названия | поля дуэли + `revealedSituationIndices` | канон → ассоциация + `раскрытиеСитуации` |
| прошедшие раунды, роли, паузы/протесты | `roundDurations` / `roundRoles` / `pauseProtestEvents` (+ копии на дуэли) | канон → **СобытиеПротокола** |
| голоса текущей формы | `refereeVotes[].vote` при `phase=judges` | канон → **Судья.голос** + событие `голос` |
| **фаза, остатки бубликов, раунд, чей ход** | `phase`, `time0`/`time1`, `roundStartRemaining0/1`, `current_round`, `current_player` | сейчас **оставить в LS**; без этого второго экрана минуты нет |
| выбранная колонка | `currentDuel` (индекс массива) | вопрос §4.2: нужен id **Поединок**, не индекс |
| подсветка слота судьи, `visible` формы | `activeReferee`, `refereeVotes[].visible` | UI-снимок |
| кнопка «Вернуть голосование» | `lastCompletedDuelIndex` | UI-снимок |

`Winner`, `people`, `confirmed` — **не решать здесь**; уже вопросы §4.2.

#### Зачем сейчас LS

Тот же браузер; работает офлайн; restore мгновенный (тик уже писал JSON). После restore не нужно ждать API.

#### Зачем БД

Другой ноут / другая вкладка / другой орг; не потерять бой, если почистили LS; часы на втором устройстве (проектор, запасной ноут). Канон (состав, судьи, ситуация, лог) после переноса уже переживает устройство. **Минуты на бубликах — нет**, если снимок часов только в LS.

#### Предложение (к обсуждению)

1. **Канон боя** (состав, судьи, ситуация, лог событий) — уже едет в БД; restore канона с сервера. Это закрывает «продолжить сетку и протокол», не закрывает «продолжить тикающие минуты».
2. **Снимок часов** (`phase`, `time0`/`time1`, `current_round`, `current_player`; опц. `roundStartRemaining*`, `game_time`) — **кандидат в БД как кэш/heartbeat поединка**, не источник истины (истина — лог). Иначе второй экран поднимет состав и голоса, но **не продолжит минуты**. Альтернатива: оставить LS только для одного устройства — тогда критерий §1 «с другого устройства» сознательно **не** включает остатки таймеров.
3. **Не тащить в БД:** ключи Google Live (`ub-timer-live-protocol-*`), кэш встреч `sessionStorage` (`ub-timer-composition-meetings-v1`), `excludedPersonIds` (и сейчас вырезаются из payload, не переживают restore).

Три варианта снимка таймера (выбрать на шаге 1, не молча):

| | Только LS | LS + heartbeat в БД | Полный снимок сессии в БД |
|--|-----------|---------------------|---------------------------|
| Что | как §4.2 сейчас | узкий кэш на **Поединок**: фаза + остатки + раунд + чей ход; писать с тика (throttle) | весь JSON `ub-timer-online-state` в таблицу |
| Второй экран | состав/лог да; минуты нет | минуты да | минуты да, плюс UI-мусор |
| Новых сущностей | нет | **нет новой таблицы**: поля/JSON на **Поединок** или отдельная витрина — дыра, спросить, не изобретать `timer_sessions` как истину | почти `timer_sessions` — против §6 |
| Конфликт двух часов | нет (разные LS) | два клиента пишут разный `phase` | то же, плюс затирание канона снимком |

**Решение (2026-10-14, спецификация timer-on-portal-db):** восстановление после закрытия вкладки — **только из localStorage** (фаза, остатки бубликов, раунд/чей ход); канон — из БД при её доступности. Вариант «LS + heartbeat» и полный снимок в БД — **отложены** (не в этой реализации). LS остаётся офлайн-снимком/резервом в любом случае.

#### Риски heartbeat

Два комплекта часов (основной + проектор, два оператора) пишут разный `phase` / разные остатки. Нужно одно из: **один активный клиент** (остальные read-only / follow) или **last-write-wins** по метке времени (проектор может отстать на тик). Без правила — гонка. Офлайн: тик без сети копит только LS; при появлении сети — один flush heartbeat, не посекундная очередь.

Не выводить остатки «из лога + wall-clock»: после закрытия вкладки часы заморожены (as-is), а не продолжают тикать в пустоту. Heartbeat хранит **замороженный** снимок, как LS.

## 5. Последовательность шагов

На каждом: обсуждение → подтверждение → код. Не делать «заодно» соседний шаг.

### Шаг 1. Разбор LS → что переезжает

Закрыть вопросы §4.2 и выбор варианта снимка часов §4.4 (только LS / LS+heartbeat / полный снимок). Зафиксировать ответы в этом файле. Код не писать, пока таблица не подтверждена.

### Шаг 2. Эндпоинт чтения состава мероприятия / поединков

**Обновлено 2026-10-14:** тонкий JSON-эндпоинт — **на хосте часов** (PHP 5.2, same-origin, общий `../db.inc.php`), **без CORS и без нового ключа** (часы и портал — соседние папки одного аккаунта Masterhost и делят одну БД). Образец прямого доступа — `points.php`.

Отдавать канон, не Google-сетку: мероприятие, список **Поединок** (порядок, тип, минуты, prep_mode, `*Id`, ситуация 0..1), актуальные **Судья**, ФИО из **Человек**. Вместимость формы 5/7/9 — как в данных/инварианте, не «команда 1/2».

Часы: пункт меню «из БД» рядом с «из Google» — загрузка встречи из БД (сначала рядом, не вместо).

### Шаг 3. Эндпоинт записи СобытиеПротокола + актуальные Судья.голос / состав

Append событий; upsert актуальных слотов **Поединок** и записей **Судья**; при смене состава — **ЖурналИзмененияПоединка**. Тот же same-origin эндпоинт на хосте часов, **без нового ключа**. Идемпотентность/порядок: в каноне идентичность протокола по моменту, не UNIQUE(seq).

**Набор событий (обновлено 2026-10-14):** начало поединка (`началоПоединка`), старт раунда, конец раунда, смена хода, пауза (**вход и выход** — два события), протест, выбор роли, **корректировка часов** (`корректировкаВремени`, прежнее/новое значение), жеребьёвка, `расчетСитуации`, `раскрытиеСитуации` (в т.ч. при выборе поединка с обычной ситуацией из БД), голос, `согласиеСудьи`, `завершение`, **решение судей зафиксировано** (`решениеСудей`). «Начало поединка» и «старт раунда» — разные события, пишутся оба.

Маппинг Live-четвёрки → канон:

| Сейчас Google | В БД |
|---------------|------|
| состав (игроки/судьи) | **Поединок** + **Судья** + журнал |
| ситуация 00 | ассоциация + `расчетСитуации` |
| Начинал = Команда N | событие `жеребьёвка` + перестановка `*Id` |
| голос | событие `голос` (новое на **каждое** изменение) + материализация текущего значения в **Судья.голос** (`duel_judges`); два источника сверяются на завершении |

Плюс то, что Google **не** хранил логом: начало поединка, пауза (вход/выход), протест, смена хода, роли, старт/конец раунда, корректировка часов, раскрытие, завершение, фиксация решения судей.

### Шаг 4. Маршрутизация записи по источнику (вместо dual-run)

**Обновлено 2026-10-14:** часы запоминают источник загрузки состава и направляют события туда же: Google-состав → Live в Google GAS (как сейчас); состав из БД → запись в БД. **Одновременной записи в оба канала нет** — иначе одно событие дублируется.

Критерий шага: один онлайн целиком в БД-режиме уходит в MySQL; смена источника применяется к последующим событиям, ранее записанное не дублируется и не переносится.

### Шаг 5. Google-режим сохраняется (cut **не** делаем)

**Обновлено 2026-10-14:** отказ часов от Google (cut) **не планируется**. Google-режим и БД-режим сосуществуют как альтернативы, выбор — при загрузке расписания. Загрузка из CSV, Live/save/clear Google остаются рабочими.

### Шаг 6. LS как офлайн-снимок (cut **не** делаем)

**Обновлено 2026-10-14:** `ub-timer-online-state` остаётся во всех режимах как локальный снимок/резерв (фаза, остатки бубликов, раунд/ход, кэш канона). В БД-режиме канон берётся из БД, при недоступной БД — из снимка. Восстановление остатков таймеров из БД (heartbeat) отложено.

### Шаг 7. Пустой исторический протокол

Факт: в дампе `СобытиеПротокола` = 0, журнал = 0; состав/голоса прошедших боёв уже лежат как **Поединок** / **Судья** (сетка Google + факты A:F), не как лог событий.

**Не обещать:**

- восстановить лог из localStorage оргов (нет выгрузки, ключ привязан к браузеру);
- восстановить посекундный протокол из сетки Google (там снимок состава и голосов, не `СобытиеПротокола`).

**Делать:** писать лог только у **новых** боёв, проведённых в БД-режиме. Историю не выдумывать. Если позже понадобится «псевдо-лог» из сетки — отдельное обсуждение, не v1.

### Шаг 8. Порядок поединков (портал + часы)

**Обновлено 2026-10-14:** кнопки перестановки поединков (вверх/вниз) — при планировании на портале (рабочее место орга) и во время онлайна в часах (участник просится в начало/конец). Порядок хранится в том же источнике, откуда читается состав, — `duels.sort_order`. Текущий поединок при перестановке в часах не теряется.

### Шаг 9. Просмотр лога на карточке мероприятия (орг)

**Обновлено 2026-10-14:** на карточке мероприятия в рабочем месте орга — read-only просмотр `protocol_events` (ход) и `duel_change_log` (правки состава/судей), фильтр по поединку, доступ только орг. Публичная «красивая» визуализация (в стиле статистики баскетбольного матча) для остальных — в идеи ([идеи.md](идеи.md)), не сейчас.

### Шаг 10. Сквозной UI-тест happy path и отчёт

**Обновлено 2026-10-14:** прогон главного сценария в БД-режиме на **тестовом мероприятии — копии реального онлайна** (классика, парный, экспресс), с проверкой восстановления (F5, закрытие вкладки, другое устройство), корректировки часов, изменений состава между поединками, порядка поединков и таймера судей (1 мин). По итогам — отчёт со скриншотами ключевых экранов в стиле happy path проекта МАИ; тестовые данные чистятся. Детальные шаги — в `openspec/changes/timer-on-portal-db/tasks.md` (группа 9).

## 7. Риски

| Риск | Что делать в плане |
|------|--------------------|
| Офлайн / LS | Без сети часы как сейчас живут в LS. Запись следует за источником; при недоступной БД события копятся в клиентской очереди и отправляются при восстановлении связи. Офлайн-sync целиком не изобретаем. |
| Два комплекта часов | Если heartbeat снимка в БД (§4.4): два клиента пишут разный `phase`/остатки. Нужен один активный клиент или last-write-wins; иначе гонка. |
| Конфликт с орг-порталом | Орги уже INSERT/DELETE `duels`. Два писателя состава: орги владеют сеткой до онлайна, часы — во время. Не затирать лог; при конфликте приоритет — последняя запись из часов. |
| Алгоритм судей в JS vs PHP | **Не дублировать** в PHP в этом плане. Эндпоинт принимает результат (список **Судья**). Иначе два расхождения. Ярлыки опыта — вычисляются в часах (§4.2). |
| PHP 5.2 на хосте часов | Эндпоинты read/write — **на хосте часов** (PHP 5.2, same-origin, `../db.inc.php`), без CORS и ключа; сложную логику сюда не тащим. Портальные экраны (лог, порядок поединков) — портал 8.3. |
| Google «Команда 1/2» | Артефакт сетки; в Google-канале маппить как сейчас, в БД — канон без команд. |
| Экспресс 5 слотов формы vs COUNT(Судья) | Не писать пустые слоты как **Судья**. |

## 8. Критерий готовности

- [ ] Часы загружают состав мероприятия **из MySQL** пунктом меню «из БД», без Google CSV (Google-режим сохранён как альтернатива).
- [ ] Ход боя пишется как **СобытиеПротокола** (включая начало поединка, корректировку часов, фиксацию решения судей; пауза — вход+выход); актуальные состав и `Судья.голос` совпадают с тем, что видно на часах.
- [ ] Запись следует за источником: Google-состав → Google, БД-состав → БД; одновременной записи нет.
- [ ] Канон из LS больше не единственная копия: второй браузер видит состав/голоса/лог.
- [ ] В LS остаётся снимок UI (фаза, остатки таймеров); heartbeat снимка в БД — отложен, не решён.
- [ ] Порядок поединков меняется на портале (планирование) и в часах (онлайн), хранится в `duels.sort_order`.
- [ ] На карточке мероприятия орг видит read-only лог (`protocol_events` + `duel_change_log`).
- [ ] Сквозной UI-тест happy path (классика/парный/экспресс) пройден, отчёт со скриншотами готов, тестовые данные очищены.
- [ ] Исторический протокол до внедрения **пустой** и это принято; из LS прошлое не «восстанавливали».
- [ ] Секреты не в git; код шагов — только после подтверждения пользователя.
