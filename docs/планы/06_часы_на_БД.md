## 1. Цель

Таймер (`timer.zaborov.ru`, `index.html` + `js/`) **читает и пишет MySQL** `u10190_ubtimer` через **тонкий PHP API** на портале (PHP **8.3**, `mysqli`). Хост часов — PHP **5.2.17**, современный API туда не кладём. Образец CORS уже есть: [`portal/api/situations.php`](../../portal/api/situations.php) (банк ситуаций на часах уже ходит в MySQL; состав поединков — ещё нет).

Google у часов: сначала **dual-run** (писать и в сетку GAS, и в БД), затем **cut** (часы больше не читают published CSV и не пушат Live в GAS).

Часть **localStorage** тоже переезжает в БД (не весь снимок сессии). Dual-run LS: писать и в LS, и в API; потом cut LS только для перенесённого. Снимок UI/часов (фаза, остатки таймеров) **остаётся в LS** — в домене это не источник истины. Нужен ли кэш/heartbeat этого снимка ещё и в БД (второй экран, очистка LS) — **к обсуждению**, §4.4.

Критерий смысла: онлайн можно провести с другого устройства/браузера, не потеряв состав, ситуацию, судей, голоса и лог боя.

| Что | Сейчас | Где в коде |
|-----|--------|------------|
| Состав встречи (поединки, игроки, секунданты, тип, Hidden / 00) | published CSV листа «состав онлайна» `gid=1172864695`; кэш встреч — **sessionStorage** | `js/schedule.js` (`loadScheduleFromGoogleLatest`, `openGoogleSchedulePicker`, `GOOGLE_COMPOSITION_CSV_URL`) |

| Файл .xlsx / .json | меню «Загрузить расписание» без Google | `schedule.js` |
| Судьи | алгоритм **в JS** (автоназначение в `schedule.js`; форма голосов `referees.js`). Не роль орга. | памятка: протокол пишет таймер; `показывалЧасы` — оператор кнопок |
| Люди на часах | локальный словарь `people` (id `p_N`, пометки novice/experienced/org/expert) в LS, не карточки MySQL | `js/state.js`, модалка «Участники и судьи» |

`js/init.js` — только UI (бублики, звуки, интро). **Не** читает и не пишет Google/LS.

### Куда уходит протокол

Четыре канала, они **не одно и то же**:

1. **Live → Google** (`js/live-protocol.js` → GAS Web App): 4 события в сетку состава — состав судей/игроков, случайная ситуация, «Начинал», голос. Ключ `LIVE_PROTOCOL_KEY` (default / localStorage). Победителя и счёт в ячейки **не** пишет (формулы таблицы).
2. **localStorage** ключ `ub-timer-online-state` — полный снимок сессии (см. §4). Пишет `saveProtocolStateToLocalStorage` (`schedule.js`); вызывают `core.js` (тик/ход/пауза), `referees.js` (голос), `toolbar-sound.js` (финиш), `protocol.js` (восстановление).
3. **Excel** «Сохранить в файл» / «Сохранить статус онлайна» — выгрузка из памяти/LS, не источник истины.
4. **MySQL** — часы **не** пишут. Орги на портале уже трогают `duels` (добавить/удалить/порядок), но **не** live-протокол.

`js/core.js`: прямой Google нет; на старте боя — `notifyLiveProtocolStarted_`; на тике/смене — `saveProtocolStateToLocalStorage`.

## 3. Канон to-be: какие сущности трогают часы

Только классы yaml. Новых таблиц (`timer_sessions`, `ПротоколПоединка`, слоты team1/2) **нет**.

| Класс | Часы | Заметка |
|-------|------|---------|
| **Мероприятие** | чтение (выбор встречи) | список / карточка для загрузки состава |
| **Поединок** | чтение + запись актуального состава `*Id`, ситуации (ассоциация), `режимПодготовки`, `длительностьРаундаМин`, вместимость формы 5/7/9 (`referee_qty` в черновике маппинга) | после жребия — перестановка `игрок1`/`игрок2`, не поле «кто начинал» |
| **Судья** | чтение + запись актуального списка и `голос` | результат алгоритма JS, не PHP; пустой слот формы — не запись; голос без ФИО — `idУчастника` null, коллегия `неизвестна` |
| **СобытиеПротокола** | запись (append-only лог) | источник истины хода боя: старт/конец раунда, смена хода, пауза, протест, голос, выборРоли, жеребьёвка, расчетСитуации, раскрытиеСитуации, завершение |
| **ЖурналИзмененияПоединка** | запись, если часы меняют состав/судей/ситуацию | история; не парные план/факт |
| **Ситуация** | чтение (join / кубик 00) | подпись = код+номер; банк на странице уже из API |
| **Человек** | чтение (ФИО слотов, справочник для назначения) | не создавать параллельный каталог `p_N` в БД |

Не трогаем этим планом: Круг / членство (кроме косвенно, если ярлыки назначения **вычислять** с портала), Видео, Регистрация, УчастиеВОрганизации, Наблюдатель, баллы/рейтинг как сущности. Победитель/счёт — вычисление по `Судья.голос`, не атрибут `Поединок`. Снимок `duel_results` — витрина, не домен; не обещать его в v1 часов без отдельного решения.

Инварианты, которые часы обязаны соблюдать при записи: `express-judges-5`, `express-no-seconds`, `qty-matches-slots`, `cannot-judge-own-duel`, `unknown-judge-placeholder`, `protocol-is-event-log`, `votes-on-judge`, `hidden-ne-random`, `round-minutes-5-4-1`. Алгоритм судей **остаётся в JS** (см. риски).

## 4. Разбор localStorage → что переезжает

Факт по `js/` (не догадка). Прямые обращения к `localStorage` / `sessionStorage` есть только в:

| Файл | Что делает |
|------|------------|
| `js/state.js` | константа `PROTOCOL_STORAGE_KEY = "ub-timer-online-state"` |
| `js/schedule.js` | **set/get** этого ключа; **sessionStorage** кэш Google |
| `js/protocol.js` | get/remove того же ключа (баннер, Excel, restore) |
| `js/live-protocol.js` | три ключа Live GAS |
| `js/core.js`, `js/referees.js`, `js/toolbar-sound.js` | только вызывают `saveProtocolStateToLocalStorage` |
| `js/init.js` | **нет** LS |

Других ключей LS в `js/` нет. Банк ситуаций LS не использует.

### 4.1. Ключи целиком

| Ключ | Где | Решение | Почему |
|------|-----|---------|--------|
| `ub-timer-online-state` | LS | **разобрать поля** (§4.2): часть → БД, часть оставить, часть — вопрос | один JSON-снимок сессии; внутри и канон, и UI |
| `ub-timer-live-protocol-url` | LS | **оставить / потом удалить** | override URL GAS; не домен. После cut Google ключ не нужен |
| `ub-timer-live-protocol-key` | LS | **оставить / потом удалить** | секрет Live; не в git. После cut — не нужен. Новый write-API — отдельный ключ в `.env` на сервере, не этот LS |
| `ub-timer-live-protocol-enabled` | LS | **вопрос** (пока dual-run — флаг устройства) | «писать в Google или нет». После cut Google флаг бессмысленен. Аналог «писать в БД» — скорее всегда да, не LS |
| `ub-timer-composition-meetings-v1` | **sessionStorage** (TTL 1 ч) | **не в БД**; умрёт с cut Google | кэш CSV встреч, не протокол |

Пишет `buildSessionStatePayload()` + `payload.duelsList` (`protocol.js` / `schedule.js`). Excel «Состояние сессии» — тот же набор ключей.

Снимок UI по-прежнему можно поднимать из LS **на этом же** устройстве. Достаточно ли этого для «продолжить минуты на втором экране» — **к обсуждению**, §4.4.

#### Неясно — вопросы пользователю (не класть в БД молча)

1. **`people` + `peopleNextId` + пометки `experience` (новичок / опытный / орг / судья ФУБ)?** В домене ярлыки **вычислимы**, не колонки. Сейчас они ручные на часах и живут в LS, ими кормится автоназначение. Варианты: (а) сессия-only UI, не в БД; (б) читать `Человек.активен` + круги/статистику с API и убрать ручные радио; (в) оставить ручные пометки только в LS этого браузера.
2. **`duelAssignments.confirmed` (зелёные ячейки «подтвердили слот»)?** Нет в домене. Сессия UI или писать в журнал?
3. **`excludedPersonIds` («не может на этот поединок»)?** В каноне уже: только сессия таймера, **не** сохраняются при restore из LS — и сейчас **вырезаются** из payload. Не переносить.
4. **`Winner` на `duelsList`?** Не сущность и не атрибут **Поединок**. Считать по голосам. Снимок `duel_results` для рейтинга — отдельное решение, не часть часов v1 без подтверждения.
5. **`currentDuel`?** Индекс выбранной колонки в UI. Для «продолжить с другого ноутбука» нужен id **Поединок** в БД, не индекс массива. Класть «текущий бой» в LS как UI или выводить из незакрытого лога?
6. **`currentRoundRole1/2` в `idle`?** Последние выбранные роли до/после боя. Это уже должно быть событием `выборРоли`, или достаточно UI?
7. **Исторический JSON в чужих браузерах оргов?** Мы **не** собираем LS с устройств. Восстановление прошлых онлайнов из LS **не обещаем** (нет фактов, что слепок где-то лежит). См. шаг 8.

### 4.3. Dual-run и cut для LS

Отдельный шаг внедрения (после того как API записи жив):

1. Подтвердить таблицу §4.2 и ответы на вопросы §4.2.
2. **Dual-run LS:** каждое изменение канона писать **и** в LS (как сейчас), **и** в API. Снимок UI — только LS.
3. Проверка: второй браузер поднимает состав/голоса/лог из БД; первый после F5 не расходится.
4. **Cut LS** только для перенесённых полей: в `ub-timer-online-state` оставить UI-снимок (фаза, time0/1, current_round, …), не дублировать весь `duelsList` как истину. Баннер restore канона — из API.

Не cut-ать LS раньше cut Google, если dual-run Google ещё читает контекст колонок из сессии загрузки.

### 4.4. Восстановление вкладки (**к обсуждению**, не канон)

Факт as-is: закрытие вкладки / F5 не теряет бой, если тот же браузер. Ключ `ub-timer-online-state`. Пишет `saveProtocolStateToLocalStorage` (тик раунда, ход, пауза, голос, финиш, выбор поединка). При загрузке `checkRestoreProtocolBanner` показывает баннер, если в LS есть `duelsList` и хотя бы одно из: фаза `round`/`judges`, «реальные» данные протокола (`Winner` / `RoundDurations` / `JudgeVotes`), словарь `people`. По «Восстановить» — `restoreProtocolStateFromLocalStorage` → `duelChoosed` → `applyRestoredSessionState`. Часы после restore **на паузе** (`clock_is_active = false`); остатки минут — как в последнем тике, не вычитаются по wall-clock.

Чтобы **продолжить тот же бой** на этом устройстве, restore реально поднимает:

| Нужно продолжить бой | Откуда в LS | Уже в плане 06 |
|----------------------|-------------|----------------|
| список поединков, имена, тип, минуты, Hidden | `duelsList` | канон → **Поединок** |
| состав слотов и судьи | `duelAssignments` (+ `people` как локальный справочник) | канон → **Поединок** `*Id` / **Судья** / **Человек**; `people` — вопрос §4.2 |
| ситуация, раскрытие названия | поля дуэли + `revealedSituationIndices` | канон → ассоциация + `раскрытиеСитуации` |
| прошедшие раунды, роли, паузы/протесты | `roundDurations` / `roundRoles` / `pauseProtestEvents` (+ копии на дуэли) | канон → **СобытиеПротокола** |
| голоса текущей формы | `refereeVotes[].vote` при `phase=judges` | канон → **Судья.голос** + событие `голос` |
| **фаза, остатки бубликов, раунд, чей ход** | `phase`, `time0`/`time1`, `roundStartRemaining0/1`, `current_round`, `current_player` | сейчас **оставить в LS**; без этого второго экрана минуты нет |
| выбранная колонка | `currentDuel` (индекс массива) | вопрос §4.2: нужен id **Поединок**, не индекс |
| подсветка слота судьи, `visible` формы | `activeReferee`, `refereeVotes[].visible` | UI-снимок |
| кнопка «Вернуть голосование» | `lastCompletedDuelIndex` | UI-снимок |

`Winner`, `people`, `confirmed` — **не решать здесь**; уже вопросы §4.2.

#### Зачем сейчас LS

Тот же браузер; работает офлайн; restore мгновенный (тик уже писал JSON). После restore не нужно ждать API.

#### Зачем БД

Другой ноут / другая вкладка / другой орг; не потерять бой, если почистили LS; часы на втором устройстве (проектор, запасной ноут). Канон (состав, судьи, ситуация, лог) после переноса уже переживает устройство. **Минуты на бубликах — нет**, если снимок часов только в LS.

#### Предложение (к обсуждению)

1. **Канон боя** (состав, судьи, ситуация, лог событий) — уже едет в БД; restore канона с сервера. Это закрывает «продолжить сетку и протокол», не закрывает «продолжить тикающие минуты».
2. **Снимок часов** (`phase`, `time0`/`time1`, `current_round`, `current_player`; опц. `roundStartRemaining*`, `game_time`) — **кандидат в БД как кэш/heartbeat поединка**, не источник истины (истина — лог). Иначе второй экран поднимет состав и голоса, но **не продолжит минуты**. Альтернатива: оставить LS только для одного устройства — тогда критерий §1 «с другого устройства» сознательно **не** включает остатки таймеров.
3. **Не тащить в БД:** ключи Google Live (`ub-timer-live-protocol-*`), кэш встреч `sessionStorage` (`ub-timer-composition-meetings-v1`), `excludedPersonIds` (и сейчас вырезаются из payload, не переживают restore).

Три варианта снимка таймера (выбрать на шаге 1, не молча):

| | Только LS | LS + heartbeat в БД | Полный снимок сессии в БД |
|--|-----------|---------------------|---------------------------|
| Что | как §4.2 сейчас | узкий кэш на **Поединок**: фаза + остатки + раунд + чей ход; писать с тика (throttle) | весь JSON `ub-timer-online-state` в таблицу |
| Второй экран | состав/лог да; минуты нет | минуты да | минуты да, плюс UI-мусор |
| Новых сущностей | нет | **нет новой таблицы**: поля/JSON на **Поединок** или отдельная витрина — дыра, спросить, не изобретать `timer_sessions` как истину | почти `timer_sessions` — против §6 |
| Конфликт двух часов | нет (разные LS) | два клиента пишут разный `phase` | то же, плюс затирание канона снимком |

**Рекомендация плана (не решение):** вариант «LS + heartbeat». LS остаётся для офлайна и мгновенного F5; heartbeat — чтобы второй экран и очистка LS не обнуляли минуты. Не класть полный JSON в БД.

#### Риски heartbeat

Два комплекта часов (основной + проектор, два оператора) пишут разный `phase` / разные остатки. Нужно одно из: **один активный клиент** (остальные read-only / follow) или **last-write-wins** по метке времени (проектор может отстать на тик). Без правила — гонка. Офлайн: тик без сети копит только LS; при появлении сети — один flush heartbeat, не посекундная очередь.

Не выводить остатки «из лога + wall-clock»: после закрытия вкладки часы заморожены (as-is), а не продолжают тикать в пустоту. Heartbeat хранит **замороженный** снимок, как LS.

## 5. Последовательность шагов

На каждом: обсуждение → подтверждение → код. Не делать «заодно» соседний шаг.

### Шаг 1. Разбор LS → что переезжает

Закрыть вопросы §4.2 и выбор варианта снимка часов §4.4 (только LS / LS+heartbeat / полный снимок). Зафиксировать ответы в этом файле. Код не писать, пока таблица не подтверждена.

### Шаг 2. API чтения состава мероприятия / поединков

Тонкий JSON на портале (PHP 8.3, CORS с `timer.zaborov.ru`), конфиг БД как у `situations.php` (`db.inc.php` вне www).

Отдавать канон, не Google-сетку: мероприятие, список **Поединок** (порядок, тип, минуты, prep_mode, `*Id`, ситуация 0..1), актуальные **Судья**, ФИО из **Человек**. Вместимость формы 5/7/9 — как в данных/инварианте, не «команда 1/2».

Часы: пункт меню рядом с «из Google» — загрузка встречи из БД (сначала рядом, не вместо).

### Шаг 3. API записи СобытиеПротокола + актуальные Судья.голос / состав

Append событий; upsert актуальных слотов **Поединок** и записей **Судья**; при смене состава — **ЖурналИзмененияПоединка**. Идемпотентность/порядок: в каноне идентичность протокола по моменту, не UNIQUE(seq). Ключ записи — секрет на сервере (аналог Live, в `.env` / `db.inc.php`), не хардкод в git.

Маппинг Live-четвёрки → канон (обсудить контракт, потом код):

| Сейчас Google | В БД |
|---------------|------|
| состав (игроки/судьи) | **Поединок** + **Судья** + журнал |
| ситуация 00 | ассоциация + `расчетСитуации` |
| Начинал = Команда N | событие `жеребьёвка` + перестановка `*Id` |
| голос | **Судья.голос** + событие `голос` |

Плюс то, что Google **не** хранил логом: пауза, протест, смена хода, роли, старт/конец раунда, раскрытие, завершение.

### Шаг 4. Dual-run (Google + БД, и LS + API)

При включённом Live: как сейчас в GAS **и** в MySQL. LS канона ещё пишется. Режим выключения Live Google не должен молча выключать БД (вопрос к шагу 1 про флаг).

Критерий шага: один онлайн на проде уходит в оба места; расхождение — баг, чинить до cut.

### Шаг 5. Cut Google у часов

Убрать загрузку состава из CSV и Live/save/clear Google из меню часов. GAS Web App для Live часов не держать обязательным. Лист Google может жить для людей/архива — это не этот план.

Банк: страница уже на API; `schedule.js` перестать join-ить CSV банка.

### Шаг 6. Cut LS для перенесённого

См. §4.3. Оставить в LS только UI-снимок.

### Шаг 7. Пустой исторический протокол

Факт: в дампе `СобытиеПротокола` = 0, журнал = 0; состав/голоса прошедших боёв уже лежат как **Поединок** / **Судья** (сетка Google + факты A:F), не как лог событий.

**Не обещать:**

- восстановить лог из localStorage оргов (нет выгрузки, ключ привязан к браузеру);
- восстановить посекундный протокол из сетки Google (там снимок состава и голосов, не `СобытиеПротокола`).

**Делать:** с dual-run писать лог только у **новых** боёв. Историю не выдумывать. Если позже понадобится «псевдо-лог» из сетки — отдельное обсуждение, не v1.

## 7. Риски

| Риск | Что делать в плане |
|------|--------------------|
| Офлайн / LS | Без сети часы как сейчас живут в LS. Dual-run: очередь на API при восстановлении связи — обсудить, не писать сложный офлайн-sync молча. После cut канона из LS офлайн-бой не попадёт в БД, пока нет сети. |
| Два комплекта часов | Если heartbeat снимка в БД (§4.4): два клиента пишут разный `phase`/остатки. Нужен один активный клиент или last-write-wins; иначе гонка. |
| Конфликт с орг-порталом | Орги уже INSERT/DELETE `duels`. Два писателя состава. Нужны: кто владеет актуальной сеткой во время онлайна (часы), кто до (орги); не затирать лог. |
| Алгоритм судей в JS vs PHP | **Не дублировать** в PHP в этом плане. API принимает результат (список **Судья**). Иначе два расхождения. Ярлыки опыта — вопрос §4.2. |
| PHP 5.2 на хосте часов | API только на портале 8.3. |
| Google «Команда 1/2» | Артефакт сетки; в dual-run маппить как сейчас, в БД — канон без команд. |
| Экспресс 5 слотов формы vs COUNT(Судья) | Не писать пустые слоты как **Судья**. |

## 8. Критерий готовности

- [ ] Часы загружают состав ближайшего (и выбранного) мероприятия **из MySQL**, без Google CSV.
- [ ] Ход боя пишется как **СобытиеПротокола**; актуальные состав и `Судья.голос` совпадают с тем, что видно на часах.
- [ ] Dual-run на одном боевом онлайне сверен; затем Google у часов отключён.
- [ ] Канон из LS больше не единственная копия: второй браузер видит состав/голоса/лог.
- [ ] В LS остаётся снимок UI (фаза, остатки таймеров) — подтверждено таблицей §4; heartbeat того же снимка в БД — **к обсуждению** §4.4, не решено.
- [ ] Исторический протокол до dual-run **пустой** и это принято; из LS прошлое не «восстанавливали».
- [ ] Секреты не в git; код шагов — только после подтверждения пользователя.
